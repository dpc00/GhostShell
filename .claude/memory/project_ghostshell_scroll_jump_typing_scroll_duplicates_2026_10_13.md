**His reports (2026-10-13, in his words):** "many times it positions me up at 1/3 of the scrollback, out of the blue, for no visible reason; then I have to scroll back down to find the command line." And: "many times when I began to type on the command line, the text position went down to where the command line was above the top of the tab-view, causing me to have to pull down the view to see what I was typing." Same family as [[ghostshell-follow-patch-2026-10-03]] (jump to "1/3 of tab contents", partly fixed, cause of unprompted drifts never found) and the 0.2.1 release note about Claude Code redrawing its whole conversation in one frame.

**New evidence from the Claude tab itself (same day):** the tab text contains repeated blocks, not just repeated lines. A scan of the 338-line view found an 18-line block (my status message, a tool call, its result, the next two tool calls) appearing twice with a fixed offset of 30 lines, with a permission-prompt box (11 lines) between the copies; a 5-line block repeated at offset 5 around a background "Monitor started" notice; a few 4-line repeats at offsets 16 to 38. Real repeats (the same tool-call echo "Called sublime-mcp-portable-4200 (ctrl+o to expand)" six times) are separate calls, not duplicates. Viewport at the time: about 39 rows by 92 columns.

**Hypothesis (not proven):** Claude Code keeps a live area at the bottom (status, pending tool call, permission box, input line) and updates it by moving the cursor up N lines and rewriting. When that area changes height (a permission box appears or goes away, a background notice arrives) or is taller than the visible rows, GhostShell leaves the old copy in the tab text and the new copy lands below it. A reprint grows the buffer by several screens in one frame, so the Sublime viewport (which keeps its pixel position) ends up a third of the way down: that would explain the jumps. Typing then makes Sublime scroll to the caret, which for the Claude tab (`tui_owns_scroll`) may be the wrong row, which would explain the second symptom. Check both against the code before believing this.

**How to apply / next steps:** (1) rebuild a recorder (the old `gs_recorder.py` is gone; design: wrap `_set_viewport` and `_set_auto_follow` in the main Sublime via eval_python, ring buffer of the last minute, dump to a jsonl file on a viewport jump larger than N px or when the caret is above the viewport top, with an automatic off-switch after a few hours; never leave it on without a timer, see [[feedback_never_leave_input_logging_on_2026_10_09]]). Also record, per frame, the PTY rows against the viewport rows. (2) Reproduce the duplicates in a plain Windows Terminal with the same Claude Code to see whether the duplicate blocks exist there; if not, the fault is in how `ai_terminal.py` applies cursor-up plus erase to the tab text. (3) Look at `_keep_tail_after_reprint`, `_settle_viewport` and the caret rules for `tui_owns_scroll` tabs for the typing symptom. Do not release anything without his confirmation after longer use.
